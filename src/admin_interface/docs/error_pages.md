Ophix generates static HTML error pages styled with the active theme. Because these pages
are served directly by nginx — not by Django — they display correctly even when the
application process is down (the 503 case in particular).

The `generate_error_pages` command is provided by `ophix-admin-interface`. The nginx
configuration and the automatic call during installation are handled by `ophix-server-base`.

---

## How error pages are generated

`generate_error_pages` renders a standalone HTML template for each error code, baking the
active theme's colours in as inline CSS variables. The output is written to
`INSTALL_DIR/static/error_pages/` — one file per code:

```text
INSTALL_DIR/static/error_pages/
    400.html
    403.html
    404.html
    500.html
    503.html
```

The nginx configuration generated by `run_install` includes `error_page` directives that
point to these files. 502 and 504 responses are mapped to the 500 and 503 pages
respectively. The 503 page is served via the `location /static/` alias, so it is
available even when Gunicorn is down.

Dark mode in the error pages responds to the operating system setting
(`@media (prefers-color-scheme: dark)`) rather than the in-admin toggle, since there is
no JavaScript available on a static page.

---

## Automatic setup via run\_install

`run_install` calls `generate_error_pages` automatically as part of the install sequence
(step 12), and the nginx configuration it generates already includes the `error_page`
directives. No manual steps are needed on a fresh install.

---

## Auto-regeneration on theme save

Once the `INSTALL_DIR/static/error_pages/` directory exists, error pages are regenerated
automatically whenever the active theme is saved — whether via the admin form, the
`set_theme` command, or `import_theme`. There is nothing to configure; it happens
silently in the background via a `post_save` signal on the `Theme` model.

On fresh installs where `run_install` has not yet been run, the signal skips silently
(the directory does not exist yet, so there is nothing to update).

## generate\_error\_pages

Generate static error pages manually. Useful after upgrading to a new version of
`ophix-admin-interface`, or when adding error pages to a server that was installed before
this feature was introduced.

```bash
ophix-manage generate_error_pages
```

Generate specific codes only:

```bash
ophix-manage generate_error_pages --codes 404,500,503
```

Write to a custom directory instead of `INSTALL_DIR/static/error_pages/`:

```bash
ophix-manage generate_error_pages --output-dir /path/to/error_pages/
```

| Option | Description |
| --- | --- |
| `--codes <list>` | Comma-separated HTTP status codes to generate. Default: 400,403,404,500,503 |
| `--output-dir <dir>` | Output directory. Default: `INSTALL_DIR/static/error_pages/` |
| `--quiet` | Suppress per-file output |

## Adding error pages to an existing server

If your server was installed before error pages were introduced, `run_install` was not
called with the new nginx template, so the `error_page` directives are absent from your
nginx configuration.

**Step 1 — Generate the pages:**

```bash
ophix-manage generate_error_pages
ophix-manage collectstatic --noinput
```

**Step 2 — Add nginx directives manually.** The `error_page` lines belong inside the
`server` block, before the `location /` block. A complete server block looks like this
(your paths will differ — check `INSTALL_DIR` in your `.env`):

```nginx
server {
    listen 443 ssl;
    server_name myserver.example.com;

    ssl_certificate     /home/ophix/myserver/ssl/certs/myserver.crt;
    ssl_certificate_key /home/ophix/myserver/ssl/private/myserver.key;

    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    access_log /home/ophix/myserver/logs/myserver.access.log;
    error_log  /home/ophix/myserver/logs/myserver.error.log;

    # Custom error pages — served directly from static files
    # (503 is served even when Gunicorn is down because /static/ is a direct alias)
    error_page 400 /static/error_pages/400.html;
    error_page 403 /static/error_pages/403.html;
    error_page 404 /static/error_pages/404.html;
    error_page 500 502 /static/error_pages/500.html;
    error_page 503 504 /static/error_pages/503.html;

    location / {
        proxy_pass         http://unix:/home/ophix/myserver/run/myserver.sock;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }

    location /static/ {
        alias /home/ophix/myserver/static/;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    location /media/ {
        alias /home/ophix/myserver/media/;
    }
}
```

The 503 page works when Gunicorn is down because `error_page 503` triggers an internal
nginx redirect to `/static/error_pages/503.html`, which is matched by `location /static/`
— a direct filesystem alias, not a proxy pass. The 502 and 504 codes are mapped to the
500 and 503 pages respectively.

**Step 3 — Reload nginx:**

```bash
sudo nginx -t && sudo systemctl reload nginx
```

After this, future theme changes will keep the pages in sync automatically (see
[Auto-regeneration on theme save](#auto-regeneration-on-theme-save) above).
